# P2P Guard

Браузерное расширение для трейдеров **Binance P2P**: при открытии ордера поверх
страницы появляется досье на контрагента — чёрный список, отзывы, статистика
сделок, реквизиты и риск-скор. Плюс командная работа и админ-панель.

Аналог BybitEye/TradeCode, только под Binance и со своим бэкендом.

```
p2p-guard/
├── backend/     Node.js + Fastify + Prisma + PostgreSQL — API и общая база
├── extension/   Chrome MV3 + React — панель в ордере и попап
├── admin/       React + Vite — админ-панель
├── PLAN.md      архитектура, модель данных, риск-скор, этапы
└── docker-compose.yml
```

---

## Быстрый старт

### 1. База

```bash
docker compose up -d
```

Postgres поднимется на **localhost:5435** (порт нестандартный, чтобы не
конфликтовать с локально установленным Postgres).

### 2. Бэкенд

```bash
cd backend
cp .env.example .env
npm install
npm run db:push      # создать таблицы
npm run seed         # админ + демо-команда + токен доступа
npm run dev          # http://localhost:4000/v1
```

`npm run seed` печатает две вещи — и это **разные учётные записи**:

| | Для чего | Куда входить |
|---|---|---|
| Администратор (UID `100000001`, пароль `admin12345`) | управление системой | только админ-панель |
| Токен доступа | активация расширения | попап расширения |

UID администратора синтетический и ни к какому аккаунту биржи не относится.
**В расширение под ним входить не нужно** — оно честно скажет «разные
аккаунты», потому что запросы к бирже пойдут от реального UID браузера, а
отзывы запишутся на админа. Трейдер активирует расширение токеном, и его
учётка создаётся уже с настоящим UID Binance.

Логин и пароль администратора меняются в `.env`.

### 3. Админ-панель

```bash
cd admin
npm install
npm run dev          # http://127.0.0.1:5174
```

Вход — UID и пароль администратора (из seed).

Порт 5174 зафиксирован (`strictPort`): ровно он прописан в `CORS_ORIGINS`
бэкенда. Слушаем на `127.0.0.1`, а не на `localhost`, — иначе Vite поднимается
только на IPv6 и часть клиентов получает «connection refused».

### 4. Расширение

```bash
cd extension
npm install
npm run build:prod   # сборка для установки (~200 КБ; npm run watch — для разработки)
```

Дальше в Chrome:

1. Открыть `chrome://extensions`;
2. Включить тумблер **«Режим разработчика»** в правом верхнем углу;
3. Нажать **«Загрузить распакованное расширение»**;
4. Выбрать папку `extension/dist` (именно `dist`, не `extension`);
5. Закрепить значок P2P Guard на панели (иконка пазла → булавка).

Затем: клик по значку → вкладка **«Активация»** → вставить токен из `npm run seed`,
придумать пароль (от 8 символов) → **Активировать**. UID Binance подставится сам,
если вы вошли на binance.com в этом браузере; иначе его можно ввести вручную на
вкладке «Вход».

После активации расширение работает **и без страницы ордера**: в попапе
можно найти контрагента по UID, нику или номеру карты и поставить отзыв
последнему, с кем прошла сделка.

**Панель на странице Binance по умолчанию выключена.** Расширение не выводит
на биржу ничего, пока пользователь сам не включит это в «Настройках» →
«Панель на странице ордера». До этого момента вся работа идёт через попап.

**Если что-то пошло не так**

| Симптом | Причина |
|---|---|
| «Сервер P2P Guard недоступен» | не поднят бэкенд — `cd backend && npm run dev` |
| Панель не появляется на ордере | она выключена по умолчанию — включите тумблер «Панель на странице ордера» в настройках |
| По контрагенту нет статистики биржи | вы не вошли на binance.com — попап покажет это и предложит войти |
| После правки кода ничего не изменилось | пересоберите и нажмите ⟳ на карточке расширения в `chrome://extensions` |
| Ошибка про `_locales` при загрузке | у вас старая сборка: пересоберите `dist` заново |

### 5. Посмотреть весь интерфейс без Binance и без базы

```bash
cd extension
npm run preview      # → extension/preview/dist/index.html
```

Самодостаточный HTML: открывается двойным кликом, ни сервера, ни базы не нужно.
Рендерит **настоящие** компоненты всех трёх частей продукта — панель
(`src/content/Panel`), попап (`src/popup/App`) и админку (`admin/src/App`) —
поверх заглушек `chrome.*` и `fetch`. То есть показывает именно то, что увидит
пользователь, а не отдельно нарисованный макет.

Живые: переключение сценариев (мошенник / чистый контрагент / загрузка / нет
авторизации), состояние сессии биржи (есть / не вошёл / другой аккаунт),
светлая и тёмная тема, отзывы с категориями, заметка команды, чёрный список,
шаблоны, вкладки попапа и разделы админки. Кнопка «Переоткрыть попап»
показывает, что состояние переживает закрытие.

Удобно для демонстрации: не нужен ни живой ордер, ни аккаунт на бирже.

## Как это работает

1. Пользователь открывает страницу ордера на `p2p.binance.com`.
2. Service worker расширения ловит `orderNo` из URL и запрашивает у **приватного
   API Binance** детали ордера и профиль контрагента — под cookie самого
   пользователя, внутри его браузера. Сессия биржи никуда не пересылается.
3. Нормализованные данные (UID/ник контрагента, сумма, статус) уходят на наш
   бэкенд в `POST /v1/counterparties/lookup`.
4. Бэкенд собирает досье: чёрный список (общий + командный), отзывы всех
   пользователей, заметку команды, статистику сделок по нашей базе, реквизиты,
   и считает риск-скор.
5. Content script рисует карточку в Shadow DOM поверх страницы.

Из чата ордера (перехват WebSocket в page-world) вытягиваются карты и телефоны
и привязываются к контрагенту — так ловится смена реквизитов и совпадение
реквизита с уже известным мошенником.

## Возможности

**Панель в ордере**
- Досье контрагента: ник, UID, страна, заглушка аватара (фото биржа не отдаёт).
- Статус в двух базах: своя (Мошенник / Мороз / Не в ЧС) и Telegram-ЧС.
- Риск-скор 0…100 с расшифровкой факторов — видно, почему именно такой балл.
- Категории жалоб: мошенник, мороз, грязь, невыполнение условий, художник,
  неадекват, комментарий. У каждой свой вес в риск-скоре.
- Отзывы: свои, командные и всех пользователей базы; автор маскируется.
- Заметка команды по контрагенту.
- Статистика Binance: средний чек и оборот (общий / 30 дней), ордеров
  (всего / 30 дней), исполнение за всё время и за 30 дней, дни с регистрации
  и с первого ордера, среднее время перевода и оплаты, подписчики и сколько
  человек занесли контрагента в блок.
- Страна регистрации аккаунта — только по данным биржи. Регион телефонного
  номера показан отдельно, рядом с самим номером: это разные вещи, и одно
  за другое не выдаётся.
- Верификации: почта, SMS, подтверждение личности.
- Отзывы самой биржи отдельным блоком, отрицательные сверху.
- Реквизиты показываются целиком: номер нужно сверять с тем, что прислали
  в чат, а по звёздочкам этого не сделать.
- Ордеры: активные / всего / команда / ваши, плюс таблицы «Общие» и «Команда».
- Реквизиты, замеченные в чате, с пометкой «в ЧС» и предупреждением о подмене.
- Быстрые ответы (шаблоны) в один клик.
- Быстрые ответы: подставляются в поле чата Binance или отправляются сразу —
  выбор в настройках. При отправке результат проверяется по факту, а не
  показывается на веру.
- Размещение панели: **под чатом** (ужимает переписку и занимает низ колонки),
  **слева от чата** или **свободно**. Ширина и высота чата настраиваются
  ползунками; пока они не тронуты, вёрстка биржи не меняется вовсе.
- Панель перетаскивается и сворачивается в кнопку с цветовым индикатором риска.

**Попап — две вкладки, всё остальное в ордере**
- **Оценить**: отзыв последнему контрагенту, с кем прошла сделка, и список
  своих отзывов. Поиск по UID, нику или номеру карты — там же.
- **Настройки**: тема, размещение панели и размеры чата, поведение шаблонов,
  синхронизация ордеров, адрес сервера. **Команда** и **Шаблоны** свёрнуты
  внизу — редкие операции не занимают главный экран.
- **Статус сессии биржи** и **статус вкладки**: сразу видно, вошли ли вы в
  Binance, распознан ли ордер и определился ли контрагент автоматически.
- **Состояние переживает закрытие**: активная вкладка и открытое досье
  восстанавливаются мгновенно, свежие данные подтягиваются фоном.
- **Команда**: **создать свою** (вы становитесь тимлидом) или вступить по
  токену; состав со статистикой, выдача токенов, выход из команды.

**Команды**
- Общая база отзывов, ЧС и заметок внутри команды.
- Тимлид выдаёт токены на вступление и исключает участников.
- Статистика по каждому участнику: объём, успешные и отменённые сделки.

**Админ-панель**
- Сводка: пользователи, обороты, контрагенты, отзывы, ЧС.
- Пользователи: поиск, блокировка с причиной, роль, команда, сброс пароля.
- Карточка пользователя: объём торгов, успешные/отменённые сделки и **с кем
  именно** он торговал (топ контрагентов с пометкой ЧС).
- Токены доступа: выдача, лимит использований, срок, отзыв.
- Команды: создание, назначение тимлида, удаление.
- Подписки: продление, смена плана, отмена (сейчас все на FREE, ограничения
  не применяются).
- Аудит всех административных действий.

## Оформление

Единые дизайн-токены на все три части продукта: панель, попап и админка берут
цвета из одного места (`extension/src/shared/theme.ts`, `admin/src/styles.css`).

- **Светлая тема по умолчанию**, тёмная и «как в системе» — по переключателю.
  Смена темы в попапе доезжает до уже открытой панели без перезагрузки страницы.
- **Прямые углы**: закруглений нет нигде, интерфейс собран из плиток. Единственный
  круг — спиннер загрузки: вращающаяся квадратная рамка читается как баг вёрстки.
- **Иконки — инлайновые SVG**, наследуют цвет текста. Эмодзи не используются:
  они по-разному выглядят в каждой ОС и не подчиняются теме.
- **Шрифт — IBM Plex Sans**, вариативный (одним файлом все начертания, жирный не
  «подделывается» браузером). Лицензия SIL Open Font License 1.1, файл лежит в
  `extension/public/fonts/` и `admin/public/fonts/`.
- Вместо аватара — заглушка с первой буквой ника: биржа фотографий не отдаёт, а
  рисовать сгенерированное лицо несуществующего человека нечестно.

## Безопасность

- Cookie-сессия Binance **не покидает браузер** — иначе антифрод биржи банит
  аккаунты пользователей.
- JWT: access 15 минут, refresh 30 дней с ротацией и детектом переиспользования
  (повторное предъявление отозванного токена гасит всю цепочку).
- Пароли — `scrypt` из стандартной библиотеки Node, без нативных модулей.
- Учётка жёстко привязана к UID Binance (`X-Binance-Uid`, при несовпадении 409).
- Роли `USER / TEAM_LEAD / ADMIN`, изоляция командных данных на уровне сервисов.
- helmet, CORS-allowlist, rate-limit (жёсткий на `/auth/*`), zod-валидация
  всех входов, единый формат ошибок, аудит-лог.
- Токены доступа хранятся в базе только хэшем — сырое значение показывается
  один раз при выпуске.

## Сессия Binance

Все запросы к бирже уходят **из браузера пользователя под его же кукой**
(`credentials: 'include'`). Сервер P2P Guard сессию биржи не видит никогда —
серверные запросы с чужой сессией ловит антифрод и банит аккаунты.

Отсюда следствие: пока пользователь не вошёл на binance.com, статистики не
будет. Расширение это показывает явно, а не отдаёт молча пустую карточку:

| Что видит расширение | Что показывает |
|---|---|
| куки сессии нет | «Вы не вошли в Binance» + кнопка **Войти в Binance** |
| вошёл, UID совпадает с учёткой | зелёная строка «Сессия активна — UID …» |
| вошёл другим аккаунтом | «Разные аккаунты»: запросы уйдут от одного UID, а отзывы запишутся на другой |

**Пароль от биржи расширение не спрашивает и не хранит.** Кнопка «Войти в
Binance» открывает настоящую страницу входа `accounts.binance.com`. Иначе и
быть не может: куку должен поставить сам Binance, а форма входа внутри
расширения — это и повод для бана в Chrome Web Store, и подарок фишерам.

**Смена аккаунта отслеживается.** Подсмотренные у страницы заголовки
(`csrftoken`, `device-info`, `bnc-uuid`) хранятся вместе с отпечатком сессии,
которой они принадлежат. Если пользователь перелогинился, старые заголовки
выбрасываются — иначе биржа отклонит запрос с чужим `csrftoken`.

## Приватный API Binance

Весь контакт с биржей собран в одном файле — **`extension/src/background/binance.ts`**.

### Что сверено по внешним источникам

| Что | Источник |
|---|---|
| Статусы ордера: `PENDING`, `TRADING`, `BUYER_PAYED`, `DISTRIBUTING`, `COMPLETED`, `IN_APPEAL`, `CANCELLED`, `CANCELLED_BY_SYSTEM` | [официальная документация C2C](https://developers.binance.com/docs/c2c/rest-api) |
| Поля ордера: `orderNumber`, `advNo`, `tradeType`, `asset`, `fiat`, `amount`, `totalPrice`, `unitPrice`, `createTime`, `counterPartNickName` | там же |
| Профиль контрагента: `POST /bapi/c2c/v2/friendly/c2c/user/profile-and-ads-list` с `userNo`; поля `nickName`, `registerDays`, `monthOrderCount`, `monthFinishRate`, `positiveRate`, `userType`, `userDetailVo` | [datawookie/binance](https://rdrr.io/github/datawookie/binance/src/R/p2p.R), [binance-p2p-api](https://pkg.go.dev/github.com/binance-converter/binance-p2p-api) |
| Список эндпоинтов C2C, поле `completedOrderNumOfLatest30day` | [официальный binance-skills-hub](https://github.com/binance/binance-skills-hub/blob/main/skills/binance/p2p/SKILL.md) |

Все восемь документированных статусов покрыты картой преобразования и
зафиксированы тестом (`extension/tests/binance.test.ts`) — если карту случайно
сломают, тест это поймает.

### Что остаётся непроверенным

На **живом ордере** адаптер ещё не гонялся: для этого нужен реальный аккаунт с
открытой сделкой. Риск снижен архитектурно — расширение не полагается на
угаданные пути. Источники данных по убыванию надёжности:

1. **Пассивный перехват** — страница сама вызывает свой API, `page-hook.js`
   отдаёт нам ответы. Работает независимо от того, как сегодня называются
   эндпоинты: объект распознаётся по форме, а не по URL.
2. **Активный запрос** — если перехвата не случилось, пробуем известные пути.
3. **Разбор DOM** — ник и UID видны на самой странице.
4. **Ручной ввод UID** — если не сработало ничего.

Первый и третий способы от переименования эндпоинтов не страдают, поэтому
базовый сценарий должен работать и без правок.

**Скорость.** Найденную пару «хост + путь» расширение запоминает в
`chrome.storage.local`, поэтому со второго раза запрос ровно один. Это не
микрооптимизация: MV3 усыпляет service worker через десятки секунд простоя, и
без сохранения он при каждом пробуждении заново перебирал бы все пути на всех
хостах — до двенадцати запросов подряд без таймаута. Внутри одного пути хосты
проверяются параллельно, у каждого запроса свой таймаут в 7 секунд. Проверка
по чистому UID из попапа идёт сразу в досье, минуя лишний поиск по своей базе.

Если что-то не сойдётся — снять HAR и поправить только этот файл:

1. Открыть реальный ордер на `p2p.binance.com`;
2. DevTools → Network → фильтр `bapi`;
3. Сверить `ENDPOINT_CANDIDATES`, `NUMERIC_STATUS` / `STRING_STATUS` и
   нормализаторы `normalizeOrderDetail` / `normalizeUserDetail`.

Разбор ответов покрыт юнит-тестами (`extension/tests/binance.test.ts`) на
нескольких вариантах формы ответа, включая вложенную и «плоскую» статистику.
Остальной код расширения при правке адаптера не меняется.

## Развёртывание в прод

Локальная схема (`docker compose` + `npm run dev`) для прода не годится: нет
HTTPS, нет миграций, секреты дефолтные. Что нужно изменить.

### 1. База данных

Управляемый PostgreSQL (Neon, Supabase, RDS, Timeweb) либо свой контейнер с
томом и бэкапами. `docker-compose.yml` из репозитория — только для разработки:
пароль в нём `p2pguard/p2pguard`.

Схему в прод накатывать **миграциями**, а не `db push`:

```bash
npm run db:deploy    # prisma migrate deploy
```

Базовая миграция `prisma/migrations/0_init` уже в репозитории. Дальнейшие
изменения схемы: `npm run db:migrate` локально → коммит → `db:deploy` на сервере.

### 2. Бэкенд

Node 20+, любой VPS или PaaS (Railway, Render, Fly, обычный сервер с systemd).

```bash
npm ci && npm run build && npm run db:deploy && npm start
```

Обязательные правки `.env`:

| Переменная | Значение в проде |
|---|---|
| `NODE_ENV` | `production` |
| `JWT_SECRET` | длинная случайная строка (`openssl rand -hex 32`), не из репозитория |
| `DATABASE_URL` | строка управляемой БД, обязательно с `sslmode=require` |
| `CORS_ORIGINS` | домен админки + `chrome-extension://<id>` после публикации |
| `ALLOW_ANY_EXTENSION_ORIGIN` | **`false`** — иначе к API пустят любое расширение |
| `SEED_ADMIN_PASSWORD` | сменить до первого `npm run seed` |

Сверху — nginx или Caddy с TLS (Let's Encrypt). HTTPS обязателен: расширение
ходит в API со страницы биржи, и браузер заблокирует http-запрос со
https-страницы.

### 3. Админ-панель

Статика, собирается в `dist/` и кладётся на любой статик-хостинг (Vercel,
Netlify, nginx, S3+CDN):

```bash
cd admin && npm ci && npm run build
```

Адрес API задаётся на экране входа («Адрес API») и хранится в localStorage —
пересобирать под каждый стенд не нужно. Панель стоит закрыть по IP или basic-auth
на уровне прокси: это вторая линия обороны поверх ролевой модели.

### 4. Расширение

```bash
cd extension && npm run build:prod
```

1. В `src/shared/storage.ts` заменить `apiBaseUrl` по умолчанию на боевой
   `https://api.вашдомен/v1` — иначе у каждого пользователя расширение будет
   стучаться в localhost.
2. В `manifest.json` убрать `http://localhost/*` из `host_permissions`.
3. Запаковать `dist/` в zip и загрузить в
   [Chrome Web Store Developer Dashboard](https://chrome.google.com/webstore/devconsole)
   — разовый взнос 5 $, ревью занимает от нескольких дней.
4. После публикации Chrome выдаст постоянный `chrome-extension://<id>` —
   добавить его в `CORS_ORIGINS` и выключить `ALLOW_ANY_EXTENSION_ORIGIN`.

Для ревью потребуется политика конфиденциальности и объяснение, зачем нужны
`cookies` и широкие `host_permissions`. Формулировка честная: расширение
читает сессию Binance **только внутри браузера пользователя**, наружу уходят
лишь UID и суммы сделок.

### 5. Эксплуатация

- Бэкапы БД: это единственное, что нельзя восстановить — вся ценность продукта
  в накопленных отзывах и ЧС.
- Логи Fastify (pino) — в файл или в сборщик; аудит админских действий уже
  пишется в таблицу `AuditLog`.
- `/health` — для проб живости у балансировщика.
- Rate-limit уже настроен (600/мин общий, 20/мин на `/auth/*`), но считает по
  токену и IP: за общим NAT ограничение общее.
